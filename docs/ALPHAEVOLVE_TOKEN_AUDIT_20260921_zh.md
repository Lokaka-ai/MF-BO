具体放大机制：

1. **以运行时间控制实验，缺少累计 token 预算。** [manifest](../runs/aq05_alphaevolve15_cpu_20260921T071425Z/manifest.json) 配置为 15 项、每项 43,200 秒、3 个 worker，最多 45 个搜索 worker。初始 500 步是每项上限；现有运行策略优先满足完整 12 小时，并允许后续提高步数上限。短时完成的数学候选使 worker 很快进入下一轮模型调用；长时间运行的候选则压低调用频率。不能仅凭 CPU/GPU 类型推断 token 成本。

2. **每个候选通常需要 4–6 次模型调用。** 正常、无重试的路径为：演化 `规划 → diff 生成 → 代码评审 → 结果摘要/潜力评级`，共 4 次；启用全局记忆的改进 `初始计划 → 记忆检索后的计划细化 → diff → 代码评审 → 结果摘要/评级`，共 5 次；初始 stepwise 草稿 `三个模块分别生成 → 合并 → 代码评审 → 结果摘要/评级`，共 6 次。失败解析、补丁重生成可能增加调用，无效执行则可能跳过结果摘要。来源：[改进路径](../runs/aq05_alphaevolve15_cpu_20260921T071425Z/code/agents/improve_agent.py)、[演化路径](../runs/aq05_alphaevolve15_cpu_20260921T071425Z/code/agents/evolution_agent.py)、[草稿生成](../runs/aq05_alphaevolve15_cpu_20260921T071425Z/code/agents/coder/stepwise_coder.py)、[评审调度](../runs/aq05_alphaevolve15_cpu_20260921T071425Z/code/engine/agent_search.py)。

3. **所有已记录调用都是同一模型、high reasoning。** 生成和反馈都用 `muse-spark-1.3-contributor`，摘要、代码评审也一样。数值评分由本地独立验证器完成，后续 LLM 摘要与潜力评级才消耗 API token。AQ05 的 rating 是结果摘要请求里的一个附加字段，并非每步另发一次独立请求；GP/KG 父节点选择也不能直接算成额外 LLM 调用。

4. **代码与历史被重复输入，并随搜索增长。** 启用 diff 只减少输出改动量，规划、diff 生成和两种评审仍会带入代码。[child memory](../runs/aq05_alphaevolve15_cpu_20260921T071425Z/code/engine/search_node.py) 会遍历子节点记录，未设置整体 token/字符截断。实际保存的 `circle_packing_rectangle` 结果评审 prompt 从最初 16,726 字符增长到末次 41,937 字符，中位数 40,393 字符；其中代码字段中位数为 35,717 字符。字符数不是 token 数，但能直接说明输入重复与增长。

5. **`max_tokens` 在当前适配器上没有生效。** [运行中的适配器](../runs/aq05_alphaevolve15_cpu_20260921T071425Z/recovery/code-02/llm/codex.py) 的 `generate()` 显式丢弃 `max_tokens`，`query()` 也没有把该参数传给传输层。单次 1,800 秒 timeout 只控制时间。`query()` 返回给上层的输入/输出 token 计数都是 0，真实的 CLI 报告值仅单独写入 `llm_calls.jsonl`；这不代表请求免费，也无法形成可靠的累计 token 限额。

HTTP 重试不是目前已记录用量的主要解释：8,158 次已结束调用中 50 次失败，比例约 0.61%；新增退避代码记录了 34 次额外传输尝试。它们确实造成中断和等待，但没有证据支持把上亿 token 主要归因于 429。底层 CLI 自身的重试次数和失败请求的实际计费不在日志中，不能据此断言失败请求成本为零。

持续搜索也不保证持续改善。`max_min_ratio` 在 08:21:25 UTC 后未刷新有效记录中的最佳分数，之后启动并完成的调用又报告了 **5,314,582 token**；`uncertainty_inequality` 在 09:03:07 UTC 后对应数字是 **4,554,593 token**。这些是截止时的边际收益观察，不能把所有探索直接称为无效消耗；当前停止策略仍要求累计运行时间。

节省用量的优先顺序：

1. 建立每项及整轮的累计 token / 调用次数上限，先补齐输入、输出、缓存、reasoning 和失败尝试用量记录；保留时间预算作为另一个独立限制。修复适配器后才能依赖输出 token 上限，仅修改现有 `max_tokens` 配置无效。
2. 为规划历史设明确长度上限，保留近期结果和关键改进；合并两阶段规划，减少重复携带完整代码。数学任务可另做单次草稿生成对照，避免每个初始草稿分成四次生成。
3. 单独评估将评审/摘要降为较低 reasoning 或成本更低的模型；结果摘要与 rating 可以继续合并。不要把独立数学评分一起省略。
4. 若目标是性价比，可增加按用量或长期无改进停止的对照配置。只减少并行数能降低单位时间的调用压力，累计成本仍应由预算控制。

以上流程、模型或停止规则的调整会改变实验条件，适合单独配置并标注；本次产物是诊断报告与统计 JSON。
